# 重试时刷新会话路由

## 目标

请求开始后如果用户修改了该会话的后续供应商，后续发生的自动重试应读取最新会话路由并切换到新供应商。

## 现状

请求开始时会把会话供应商写入路由快照。每次重试虽然会重新选路，但仍读取这个冻结快照，因此“请求先由旧供应商开始、运行中修改会话路由、修改后才重试”的请求仍会继续访问旧供应商。

## 设计范围

- 重试前根据活动请求的线程标识重新读取当前会话路由。
- 当前会话已固定供应商时重试到该供应商；取消固定时恢复跟随当前全局供应商。
- 更新重试后的路由快照，保证状态与实际供应商一致。
- 增加请求运行中修改和取消会话路由的时序回归测试。

## 非目标

- 不强制中断已经开始输出的流式响应。
- 不重放已经向客户端发送过内容的请求。
- 不改变重试次数、退避时间、可重试错误分类或新请求选路逻辑。

## 兼容性

无接口、配置或数据库迁移。行为变化只发生在请求尚可安全重试且会话路由在请求开始后发生修改时。版本选择 `patch`，因为这是现有会话路由重试语义的缺陷修复。

## 风险

并发修改路由时，重试使用进入重试选路临界区时的最新值；通过路由器现有锁保证读取路由、迁移活动计数和更新请求状态的一致性。

## 测试计划

- 单元测试覆盖请求开始后固定到其他供应商，再触发重试。
- 单元测试覆盖请求开始后取消固定，再触发重试。
- 运行 Python 和 JavaScript 全量测试、前端语法检查、PR 策略及 diff 检查。

## 实际改动

- `local_proxy/core.py`：`route_retry_to_current()` 根据活动请求的 `thread_id` 实时读取当前会话路由；供应商未变化时也刷新快照中的会话路由值，供应商变化时同步迁移活动请求计数和状态。
- `tests/test_proxy_core.py`：新增请求开始后固定供应商、取消固定供应商，以及第一次失败后的退避期间修改会话路由并验证第二次 HTTP 请求目标的回归测试。
