# 清理失联的活动请求

## 目标

避免客户端连接已经结束后，请求仍长期停留在“运行中 / 接收中”，导致活动请求数量和供应商占用状态失真。

## 现状

活动请求仅在响应流生成器的最终清理路径中移除。真实运行中已观察到两条请求在客户端连接消失、同会话后续请求已完成后，仍在内存活动列表中保留二十分钟以上；页面如实展示了服务端的陈旧状态。

## 设计范围

- 流式响应期间始终并行监听 ASGI `http.disconnect`，不依赖下一次响应发送才发现客户端断开。
- 客户端断开时取消等待中的上游流迭代，使现有响应生成器立即进入记录与清理路径。
- 活动请求结束操作保持幂等，重复或迟到的清理不得影响同供应商的其他请求。
- 断开请求沿用“客户端取消”历史结果，不伪造成功或丢弃已捕获 Token。
- 增加上游首段输出后永久等待、客户端随后断开的真实 ASGI 生命周期回归测试。

## 非目标

- 不对仍保持客户端连接的长时间上游请求设置固定总时长。
- 不改变正常请求的重试、路由、Token 统计或历史结果。
- 不修改数据库结构或回写现有记录。

## 兼容性

仅增加进程内活动状态字段和清理逻辑，配置、接口响应结构与数据库均保持兼容。属于向后兼容缺陷修复，版本选择 `patch`。

## 风险

- 并行读取断开事件必须在请求体读取完成后开始，避免与请求体消费竞争。
- 响应完成与客户端断开可能同时发生；任务收尾必须只取消仍在等待的一侧，并传播真实发送异常。
- 重复结束可能扣减其他活动请求；结束操作必须先确认请求仍在活动映射中。

## 测试计划

- 测试首段输出后上游永久等待，客户端断开仍能及时完成响应任务并清理活动状态。
- 测试断开结果写入“客户端取消”历史且上游流被关闭。
- 测试重复 `finish_request` 不会扣减同供应商的其他活动请求。
- 运行完整 Python、Node、JavaScript 语法、Python compileall 和 diff 检查。
- 用户手动重启后观察旧条目消失，新的客户端断开不再长期停留。

## 实际改动

- `local_proxy/core.py` 增加断开感知流式响应，在请求体读取完成后并行运行响应发送与 ASGI 断开监听；任一侧结束都会取消等待中的另一侧，使上游无新数据时也能进入既有记录和清理路径。
- `ProviderRouter.finish_request` 改为按活动详情执行幂等结束，并以活动详情中的实际供应商扣减计数，重复结束不会影响其他请求。
- `tests/test_proxy_core.py` 增加 ASGI 2.4 下“首段输出后上游永久等待”的真实断开回归测试，以及重复结束不误减其他请求的单元测试。
