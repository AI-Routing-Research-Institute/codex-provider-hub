# 提案：模型选择跟随供应商配置（消灭模型名翻译层）

- 状态：**待确认**（阻塞于第 7 节的三个问题）
- 提出日期：2026-09-04
- 提出人：moye12325
- 实现时转 `docs/changes/YYYY-MM-DD-<slug>.md`（type=feature，预计 minor）

## 1. 一句话陈述

**CLI 里选什么模型，请求就发什么模型（代理不篡改）；而 CLI 能选到哪些模型，由当前供应商配置决定——这家 API 有什么模型，CLI 的 `/model` 列表就有什么。**

## 2. 背景与问题本质

系统分两层：

- **配置层（已解决）**：本地代理固定监听 `127.0.0.1:17890/v1`，codex-cli 的 config.toml 永远指向代理；切换供应商（ChatGPT 中转 ↔ Claude 中转 ↔ DeepSeek 中转）只是代理内部换路由。
- **模型层（错位所在）**：CLI 认识的模型名与当前供应商认识的模型名是两套词汇表，切换后"鸡同鸭讲"。

历代补丁都在**翻译**上做文章：

| 方案 | 思路 | 代价 |
|---|---|---|
| v1.5 单值"模型重写" | 所有请求强制改成供应商声明的一个模型 | CLI 的选择权被没收（2026-09-04 用户报告的 sol→luna 切换无效 bug，#91 修复） |
| v1.6 模型映射表 | 本地名→上游名逐条翻译 | 每家每模型需人工配置，新模型漏配即漏翻译 |
| #91 修复 | 映射未匹配时透传 | 词汇表仍是两套，只是不再强改 |

本提案是第四条路：**不翻译，让两套词汇表合成一套**——CLI 的候选列表直接就是当前供应商的模型列表，选的名字天然是上游认识的名字，翻译层（映射表、单值重写）失去存在必要。架构做减法。

## 3. 用户故事（理想体验）

1. 当前在 ChatGPT 中转：CLI `/model` 列表 = 这家的模型（`gpt-5.3-sol`、`gpt-5.3-luna`…），选 `luna` 发请求，上游收到 `luna`。
2. 控制台切到 DeepSeek 中转：CLI `/model` 列表**自动变为** `deepseek-chat`、`deepseek-reasoner`…；旧会话继续用 `luna` 的请求收到上游"模型不存在"报错（或按可配置策略回落该家默认——待确认，见 §7.2）。
3. 新开会话：默认模型 = 该家声明的默认（config.toml 的 `model` 随切换写入）。
4. 全程零映射配置、零"模型重写"，代理只做透传。

## 4. 现状盘点

| 环节 | 现状 | 差距 |
|---|---|---|
| 透传（选什么发什么） | ✅ #91 后已具备（供应商不配重写即透传） | 无 |
| 供应商"模型列表"数据 | ❌ 仅有单一 `model` 字段（默认模型） | 需新增每家一份模型列表（含默认标记） |
| 控制台维护入口 | ❌ 无 UI | 供应商编辑弹窗加模型列表管理（增删、设默认、从上游拉取） |
| 切换联动：写默认模型 | ⚠️ cc-switch 的供应商 TOML 顶层 `model` 在切换时写入 config.toml | hub 控制台切换是否也写，需对齐所有权（§7.3） |
| 切换联动：写候选列表 | ⚠️ 约定已存在：`~/.codex/cc-switch-model-catalog.json`（探测工具 probe_codex_cc_switch / probe_gui_support 在读写） | **未验证 codex-cli 是否读它**——本提案唯一关键未知 |
| 代理 `/v1/models` 端点 | ❌ 未实现 | 可加：按当前供应商动态返回其模型列表 |

## 5. 关键未知与三种结局

**问题：codex-cli 的 `/model` 候选列表从哪来？**

- **结局 A（最好）**：codex-cli 读 `~/.codex/cc-switch-model-catalog.json` 或 config.toml 自定义模型列表 → 控制台维护列表 + 切换时写文件即完成联动，工作量集中在数据层与 UI。
- **结局 B（次好）**：列表写死于二进制，但 config.toml `model`（默认模型）可自定义 → 候选列表联动做不到；做"切换→新会话默认模型正确"；列表展示放控制台，CLI 里手输模型名。
- **结局 C（最差）**：列表与默认均锁死 → CLI 侧无解，维持映射表兜底（回到现状）。

**验证方法**（约两分钟）：codex-cli 敲 `/model` 看列表是否随配置变过；往 `~/.codex/cc-switch-model-catalog.json` 手写一个假模型名，重启后看列表是否多出该项。

## 6. 若结局 A 成立的实施蓝图

1. **数据**：本地供应商目录 sqlite 新增 `provider_models` 表（provider_id、model_name、is_default、sort_index），与既有 `provider_model_mappings` 同级。
2. **UI**：供应商编辑弹窗新增"模型"分区——列表增删改、默认标记、"从上游拉取"按钮（经代理转发该供应商的 `GET /v1/models`）。
3. **联动**：代理切换供应商时——
   - config.toml 写入该家默认 `model`（新会话起点；所有权规则见 §7.3）；
   - `~/.codex/cc-switch-model-catalog.json` 重写为该家模型列表（CLI 候选项）。
4. **透传收尾**：映射表与单值重写降级为兼容选项（老配置不坏），新配置引导使用模型列表；文档中"模型重写"重新定位为"未配置列表时的兜底"。
5. **测试**：切换联动写文件的单元测试；三家供应商切换场景手动验收（列表变化、透传、旧会话报错行为）。
6. 预计规模：一个完整 PR（数据 + UI + 联动 + 测试），minor。

## 7. 待确认问题（阻塞项）

1. **codex-cli `/model` 列表现状**（§5 的两分钟验证）——决定走 A/B/C 哪条路；
2. **旧会话遇未知模型的行为**：报错提示换模型（干净、符合"选什么是什么"语义，倾向此项）还是自动回落该家默认模型（顺手但隐式）；
3. **config.toml 写权限所有权**：目前归 cc-switch 管理，hub 控制台切换时写 `model` 字段需定规则（建议：hub 只写 `model` 一行，其余字段不动，后写者生效并记录日志）。
