# 时间筛选持久化与当天结束边界设计

## 背景与根因

当前前端仅把自定义范围 `{start, end}` 写入 `localStorage`。选择固定预设时只修改运行时的 `appliedTimeWindows`，没有同步存储；初始化恢复只要发现有效范围就无条件切换成 `custom`。因此“自定义 → 今日 → 刷新”会回到自定义。

自定义弹层还以当前时刻作为结束时间上限。用户若希望查询今天整天，只能把结束时间设为操作当刻；页面后续轮询得到的新记录超过该固定边界后不会显示。后端只校验起止顺序和请求历史跨度，本身能够安全接受本地当天末尾作为未来上界。

## 状态模型

每个目标继续使用现有存储键：

```text
local-proxy-time-range-<service_id>-usage
local-proxy-time-range-<service_id>-requests
```

值升级为：

```json
{
  "window": "today",
  "range": {
    "start": 1786291200000,
    "end": 1786377599000
  }
}
```

`window` 表示当前生效的预设或 `custom`，`range` 保存最近一次有效自定义范围。选择固定预设不会清空 `range`，以便用户再次打开自定义弹层时继续编辑原范围。

旧版本直接保存的 `{start, end}` 被识别为遗留结构，并规范化为 `{window: "custom", range: stored}`。无效窗口回退到目标默认值：Token 为 `today`，请求记录为 `24h`。`custom` 没有有效范围时同样回退默认值。

## 时间边界

“今日”预设保持现有动态语义：后端只使用本地当天 `00:00:00` 作为下界，不传结束上界，因此轮询会持续包含当前时刻之前的新记录。

自定义范围的前端上界改为浏览器本地当天 `23:59:59.999`。日期晚于今天仍然拒绝。时间输入精确到秒，实际允许的最大输入是 `23:59:59`；请求参数继续追加 `999` 毫秒以包含整个结束秒。

请求记录仍必须同时满足：开始时间处于最近 7 天、起止跨度不超过 7 天。未来当天上界不改变记录保留逻辑，数据库只会返回已经存在的记录。

## 交互流程

1. 应用自定义范围时保存 `{window: "custom", range}`。
2. 选择“今日、近 24 小时”等固定预设时，更新内存状态并立即保存 `{window: selected, range: previousRange}`。
3. 页面初始化读取存储，经过统一规范化后同时更新 `customTimeRanges`、`appliedTimeWindows` 和下拉框。
4. 自定义范围若结束于今天稍后时间，当前查询只返回已有记录；后续刷新自动纳入新记录，直到当天结束。

## 测试设计

- 纯函数测试本地当天末尾计算，包括 `23:59:59.999` 和次日零点边界。
- 状态规范化测试新结构的固定预设、有效自定义、无效自定义及旧结构迁移。
- 存储负载测试固定预设与最近自定义范围同时保留。
- 源码接线测试两处下拉框选择固定预设后都会调用持久化。
- 运行现有全量测试确认后端查询、请求保留和其他前端状态不受影响。

## 非目标与发布

不修改后端接口、数据库或轮询周期，不自动重启本地服务。该修复以 `patch` 版本通过现有自动发布流程交付。
